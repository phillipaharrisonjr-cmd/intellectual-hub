3. The product in one paragraph

Denali reads a bank's ACH activity (NACHA file upload first, core integration later), classifies each descriptor against rules to find the products a commercial customer runs at another institution (Worldpay merchant settlements, a UMB purchase card, Paychex payroll, a Chase lockbox), compares that with what the bank already holds, and projects the revenue the bank is missing from 90 days of flow. Each opportunity carries a score, a written explanation, evidence rows and the projection math. Bankers refer, approvers approve, and only then does anything push one-way to CRM. Every action is audited.

How a projection is built

Only rows inside the trailing 90 days count. Merchant: settlements ÷ (1 − 2.4% processing cost) → × 365/90 → × 0.34% net margin. Card: payments × 365/90 × net interchange. Payroll / lockbox / AP: runs × items × per-item + monthly fee. Loans / equipment: annual payments × balance multiple × spread. All rates live in backend/config/revenue-assumptions.json, and the 123 Ford example ($4.21M settlements → ≈$59K/yr) is pinned in a test.

6. How we build (the workflow)

  1. Align. Interview until both sides describe the finished thing the same way (grill-me).
  2. Plan. PRD → GitHub issues with acceptance criteria a test can check.
  3. Slice. Vertical slices: ACH row → rule → score → API → screen. Ugliest version end to end first.
  4. TDD. Failing test first, every time.
  5. Review and guard. Fresh-context agent reviews the diff. Git guardrails on. Humans read anything that changes money, referral state, or auth.

Bugs are removed, not fixed: each one gets BUG-NNN in backend/test/regressions.test.js and a row in backend/BUGS.md with the root cause. CI refuses red. Full text in docs/denali-engineering-workflow.md.
